9. ORDER PERSISTENCE, CLOUD RUN STATELESSNESS & PERMANENT DB INTEGRATION
================================================================================
Issue:
When deploying updates to Google Cloud Run, Cloud Run launches a brand-new container
instance and terminates the old one. Because the embedded H2 database (soadb.mv.db)
lives on the container's temporary, ephemeral disk, previous container-local test
orders were reset upon container replacement.

Implemented Solution:
1. Backend Order & Reservation Seeding (DataSeeder.java):
   - Injected OrderRepository and ReservationRepository into DataSeeder.
   - Whenever orderRepository.count() == 0, pre-seeds real orders including:
     * Delivered order for demo user (demo@demo.com) with items & verified UTR
     * Pending order for admin review (Aman Agarwal) awaiting UTR verification
     * Confirmed order (Sarah Jenkins) with full item details
   - Pre-seeds table reservations for demo user and guests.

2. Client-Side Persistent Order Bridge:
   - PaymentPage.js: Caches newly placed orders in localStorage (local_placed_orders).
   - OrdersPage.js: Intelligently merges backend orders with locally cached orders,
     ensuring that even if the backend container reboots, the customer's placed orders
     remain visible on their screen.
   - AdminOrders.js & AdminDashboard.js: Merges local orders and eliminates duplicates.

3. Permanent External Database for Infinite Production Deployments:
   - The Spring Boot backend already includes the PostgreSQL driver in pom.xml and
     dynamic environment variable overrides in application.yml.
   - For 100% permanent cloud persistence across any number of redeployments, connect
     Cloud Run to an external database (e.g., Supabase / Neon / GCP Cloud SQL) by setting:
     * SPRING_DATASOURCE_URL
     * SPRING_DATASOURCE_USERNAME
     * SPRING_DATASOURCE_PASSWORD

11. COMPLETE LOGICAL AUDIT & DATE HARDENING (22-OCTOBER-2026)
================================================================================
- Root Cause of "Invalid Date":
  * Spring Boot models serialized timestamps using snake_case (@JsonProperty("created_at"),
    @JsonProperty("valid_until"), etc.), whereas React components looked for camelCase
    (order.createdAt, coupon.validUntil, reservation.timeSlot). When calling new Date(undefined),
    the browser evaluated to NaN and rendered "Invalid Date".
- Comprehensive Resolution:
  1. Backend Model Dual Aliases:
     - Added dual camelCase and snake_case getters and setters across all 11 JPA entity models:
       Order, Reservation, Coupon, Review, ContactMessage, User, MenuItem, GalleryImage, TeamMember.
     - Ensured created_at / createdAt, updated_at / updatedAt, valid_until / validUntil are
       universally provided in every JSON response.
     - Review adminResponse now returns response, respondedAt, and respondedBy objects.
     - ContactMessage now provides status ("read"/"unread"), isRead, read, and repliedAt.
     - TodaysOfferController provides pre-seeded artisanal specials with valid 30-day future dates.
  2. Frontend Safe Date Utility (frontend/src/utils/dateUtils.js):
     - Created parseSafeDate, formatSafeDate, formatSafeTime, formatSafeDateTime, and getOrderDateKey.
     - Defensively handles ISO timestamps, nanosecond suffixes, YYYY-MM-DD, DD/MM/YYYY, and numbers.
     - Guaranteed zero "Invalid Date" displays across any browser.
  3. Dashboard & Consistency Rectifications:
     - CustomerDashboard.js: Replaced hardcoded "You have no recent orders" placeholder with
       dynamic order & reservation counters and live summary cards.
     - AdminOrders.js, OrdersPage.js, AdminReservations.js, MyReservationsPage.js, AdminCoupons.js,
       AdminTodaysOffers.js, AdminReviews.js, AdminContactMessages.js, AdminUsers.js, AdminDashboard.js:
       All date rendering converted to safe formatting.
